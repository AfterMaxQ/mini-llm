# MiniLLM：工具调用训练、蒸馏与 Agent 实验设计

版本：1.2　日期：2026-10-01　类型：项目设计规格

## 1. 要做成什么

围绕一个具体问题完成项目：在单卡 12GB 显存的预算内，专项训练能否让小模型更可靠地调用工具、完成开发任务，并降低部署成本？

主线从 Qwen3-1.7B 的官方已后训练模型出发，依次完成数据检查、训练机制验证、LoRA/QLoRA 微调、教师轨迹蒸馏、本地推理部署、BFCL 评测与 Pi 环境任务。每一步都要能用代码、原始结果和中文记录解释。

项目交付代码、配置、数据清单、逐条评测结果、实验图表和持续更新的 Word 文档。只有真实运行过、能追溯来源的结果进入经验总结与简历材料。

整个项目由当前主 Agent 执行。不得创建、调用或委派子 Agent，包括实现、检索、测试、文档和审查。需要第二次审查时由当前 Agent 重新检查源码、数据与产物。

## 2. 范围与推进方式

这是一个分阶段的架构项目。下面的阶段分别形成可验收的交付物；每个阶段再制定自己的实现计划，不把整个项目塞进一个不可检查的大任务。

| 阶段 | 主要问题 | 交付物 |
| --- | --- | --- |
| A 环境与数据 | GPU 能否训练？样本是什么？ | 环境锁定、数据检查报告、划分清单 |
| B 训练机制 | 哪些 token 产生 loss？哪些参数更新？ | 模板、mask、梯度、保存恢复的验证记录 |
| C 微调与泛化 | 改提示词和改权重分别有什么收益？ | 基线、完整 SFT、LoRA/QLoRA 对照 |
| D Agent 数据 | 通用工具数据能否迁移到 Pi？ | 执行可验证的 Pi 训练轨迹与独立任务集 |
| E 蒸馏 | 教师更强吗？哪些教师数据值得学习？ | 教师评测、生成与拒绝记录、蒸馏对照 |
| F 推理部署 | 量化、上下文和并发怎样影响能力与成本？ | 同一模型的精度与性能比较 |
| G 综合评测 | 标准成绩能否解释 Agent 实际表现？ | BFCL、Pi、通用回归与误差分析 |
| H 复盘 | 能否从证据解释每个关键选择？ | 中文报告、Word 实验档案、面试复盘 |

使用 PyTorch、Transformers、TRL、PEFT 与 bitsandbytes 进行主线训练。通过 llama.cpp 提供本地接口，Pi 负责实际 Agent 运行。训练环境先验证原生 Windows 的 CUDA 和依赖组合；原生方案无法解决兼容问题时，再单独设计 Linux 环境迁移，不直接升级或替换现有系统。

小规模实验用于检查机制。正式实验必须覆盖完整数据清单、对照条件和独立测试；不能以一次成功调用、128 条训练或一个下降的 loss 宣布能力提升。

训练、教师生成、推理和评测全部使用本机资源。训练时不停止无关程序；记录实际可用显存及资源竞争。

本项目的训练、教师生成、推理和评测全部在本机完成，不调用云模型或付费服务。允许下载公开模型、数据和依赖，以及推送本仓库。常规安装、排错、模型调整和归档由当前主 Agent 连续完成，阶段之间不要求用户介入；理解问题留作后续复习。

### 2.1 实验代码的写法与验证

实验代码采用直接实现、实际运行、根据结果修改的方式，不采用 TDD 或测试先行流程。实现计划、代码和实验笔记不安排或记录“先写失败测试—通过测试—重构”的步骤，不为遵循流程添加占位测试、mock 场景或配套单元测试体系，也不以测试覆盖率为目标。

代码以能完整跑通本轮实验、产出可核验的结果为准。保留必要的输入检查、数值断言和实际运行检查，例如监督 token 是否存在、loss 是否有限、梯度是否有效、保存加载是否一致、评测分母是否正确。数据划分、官方评测器和 Pi 任务自身的成功判据继续按实验要求执行；这些属于实验验证，不要求另建测试框架。

围绕实验问题写简洁脚本和小函数，优先使用成熟库的直接接口。参数集中保存，反复使用的逻辑再提取为共享函数；避免为假设中的需求搭建插件系统、复杂继承、依赖注入或通用工作流平台。简化代码不能删掉必要的对照、原始结果或失败记录。

源代码标识符使用英文，必要注释与说明使用中文。注释解释张量形状、监督遮罩、数据过滤理由、数值处理和实验条件；不逐行复述代码，不堆砌长篇概念说明。代码应让读者沿着数据读取、模型调用、训练或推理、结果保存的顺序看懂一轮实验。

## 3. 学习如何融入实验

每个学习单元按六步推进：先用普通语言解释问题，给出一个具体样本，指出相关张量或代码，提出可验证的预测，运行实验，再用结果修正解释。

一次围绕一个完整问题展开。例如，讲完 assistant-only loss 时，要完成消息到 token、标签遮罩、loss、梯度以及一次训练结果的对应关系，不能只解释一个术语就结束。

Codex 负责环境、数据、脚本、执行、记录、排错和图表。用户参与关键预测与结果解释，不承担反复安装依赖、整理日志等工作。用户没有反馈时，独立工程工作可以继续，理解确认栏保持“未回答”；不得替用户填写“已掌握”。

每阶段至少保留两个理解问题：一个解释机制，一个解释数据。问题应能用本阶段实际样本或图表回答，不考脱离项目的名词列表。

写作以具体事实为中心。例如“验证集工具名准确率从 a 变为 b，但两轮任务没有改善，错误主要发生在工具返回后的参数拼接”，其中数值必须来自运行结果。没有结果时只写实验问题与预期检查，不预写成功结论。

## 4. 模型、数据与统一表示

### 4.1 模型角色

学生起点为 Qwen/Qwen3-1.7B，属于已完成后训练的官方检查点，不能描述为从零训练的基座。下载时解析并保存具体 revision、tokenizer 与 chat template 的哈希。

教师候选为 Qwen/Qwen3-8B 的四位量化部署。教师和学生分时运行，先测教师在开发任务上的表现，再决定其输出是否适合作为监督。教师不优于学生时也要保留对照结果，不能默认参数更多就代表标签正确。

8B 教师在规定上下文下无法稳定推理时，改用 Qwen3-4B 并重跑教师验证。1.7B 学生在正确环境仍有可复现资源限制时，可改为 Qwen3-0.6B，但必须重新建立基线、微调和蒸馏对照。改变模型、序列长度、量化、CPU 卸载或运行环境另开运行，保留原因和原失败条件；不同学生型号不合并提升幅度。

主线固定非思考模式；工具调用和最终文本通过同一模板处理。思考模式另立实验，不能混入主线成绩。每个配置记录思考开关、采样参数、最大输出长度与停止规则。

多轮轨迹按当前 assistant 回复展开训练单元，保留完整历史与工具定义，只监督当前回复。逐条检查单元的训练前缀与非思考推理前缀相同；官方模板只增加监督标记，不改写实际渲染。记录独立轨迹数、展开单元数和监督 token 数，数据规模仍按原始独立轨迹计算。

### 4.2 数据来源

首先检查 NousResearch/hermes-function-calling-v1 的实际文件、授权和工具调用样本。其 ShareGPT 表示转换为 messages 与 tools 的结构化记录，保留原始 id、文件、版本和转换程序版本。数据集内的结构化抽取、纯 JSON 输出和工具执行样本分开统计。

Salesforce/xlam-function-calling-60k 是第二个候选来源。下载前处理其访问条件与署名要求。数据卡宣称的验证质量只能作为来源说明，不能直接当成本项目清洗后的质量。

Pi 数据来自本项目可执行任务：工具 schema、输入任务、实际调用、工具返回和最终状态一起保存。参考轨迹通过任务规则和执行结果验证；生成失败也写入生成台账。

### 4.3 单条记录的必要字段

| 字段 | 含义 |
| --- | --- |
| sample_id / source_id | 本地唯一标识与源样本标识 |
| source_revision / license | 来源版本、授权与署名信息 |
| group_id / split | 任务模板或仓库组及所属划分 |
| messages / tools | 用户、模型、工具消息与实际工具定义 |
| validation | 格式、参数、执行和最终状态的检查结果 |
| teacher_run_id | 使用教师时对应的生成运行 |
| token_count / target_token_count | 总 token 与实际监督 token 数 |
| rejection_reason | 被过滤时的原因 |

原始记录不可被清洗程序覆盖。转换错误、无监督 token、被截断的调用、丢失的工具返回都进入拒绝清单。多轮训练只接受可以完整表示的轨迹；不能把工具调用 JSON 截一半继续训练。

### 4.4 划分与泄漏检查

先划分任务组，再做训练增广。公开数据按规范化调用和任务模板分组；Pi 数据按模板及仓库族分组，保证同一任务的参数变体不跨 train、dev、test。

检查精确重复、规范化重复与近似重复。保存判定方法、阈值、命中数和处理记录；不能宣称已经排除预训练阶段的全部污染。

BFCL 的题目、答案及其改写不得进入训练和教师生成。最终测试任务冻结后不用于提示词调优、样本挑选或 checkpoint 选择。

正式公开工具数据使用嵌套的 1,000、5,000、10,000 条训练子集，观察规模变化。验证集至少 500 条，独立公开工具测试集至少 500 条。数量按清洗后独立有效样本计算，不能复制样本凑数。若有效量不足，记录覆盖缺口并扩展合规来源，不能把小样本结果标成完成正式验收。

## 5. 循序渐进的实验清单

表中的规模和参数是实验要求，不是已经获得的结果。每个实验都包含原始记录、中文解释和下一步依据。

### A. 环境与数据

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E00 | 检查 Python、GPU、CUDA 与依赖 | 记录版本、命令、退出码、设备与时间 | 区分驱动识别和 PyTorch CUDA 可用性；不把 CPU 检查当作 GPU 证据 |
| E01 | 建立独立 CUDA 训练环境 | CUDA 张量运算、反向传播、同步计时、显存分配 | 数值有限、梯度有效；保存实际 CUDA 输出和依赖锁 |
| E02 | 清洗与划分公开数据 | 样本类别、长度、工具数、拒绝原因、重复率 | 输出划分清单和处理前后数量；随机检查至少 50 条并记录问题 |

学习问题：为什么能运行 nvidia-smi 仍可能无法训练？训练集和测试集只有不同 id，为什么还会泄漏？

### B. 训练机制

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E03 | 检查消息、模板、token 与 EOS | 20 条样本，包含多轮、工具返回、空结果和长参数 | 保存可读 token/角色/mask 对照；训练与部署模板一致；调用完整结束 |
| E04 | 比较 assistant-only 与全文 loss | 相同输入和初始权重；记录参与监督的位置 | 手工计算的小批 loss 与框架值对应；padding、用户和工具消息不被误当目标 |
| E05 | 观察 LoRA 的梯度与参数变化 | 记录冻结参数、可训练参数、梯度和更新前后摘要 | 基础权重保持冻结，适配器实际更新；能解释 LoRA 初始化时部分梯度为零 |
| E06 | 对 32 条完整样本做过拟合排错 | 最多 300 optimizer steps；固定 seed 和样本 | 至少 29/32 条训练样本通过工具名和参数检查，保留初始对照；未能拟合时先排错；此实验只证明训练链路 |
| E07 | 保存、加载、继续训练 | 同一小实验；分别在保存前、加载后、续训后比较 | 适配器加载后的输出和参数对应；断点包含优化器与步数；续训失败有记录 |

使用一个实际样本解释输入形状、labels 的 -100、下一 token 预测和梯度更新。LoRA 的增量权重为 B×A×alpha/r；检查的是正确的冻结和更新关系，不要求第一步每个 LoRA 参数都有非零梯度。

### C. 基线、微调与泛化

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E08 | 原模型与提示词基线 | 在 dev 上冻结零样本和少样本提示；所有后续模型沿用固定方案 | 保存每条调用、无工具判断和错误；不能只展示成功例子 |
| E09 | 完整 QLoRA SFT 与规模比较 | 1k、5k、10k 嵌套数据；固定主要配置 | 完成实际训练与验证曲线，记录泛化和过拟合；正式主线至少使用 10k 有效样本 |
| E10 | BF16 LoRA 与 NF4 QLoRA 比较 | 5k 相同样本、同一 rank、步数和模板 | 比较质量、峰值显存、吞吐与耗时；显存不足时记录完整失败配置 |
| E11 | rank 和学习率的受控实验 | rank 8/16/32 固定学习率；再固定 rank 比较 5e-5/1e-4/2e-4 | 每次只改一类变量；只用 dev 选择配置；保存全部运行，不只保存最优值 |
| E12 | 数据质量对照 | 等量且类别匹配的数据；比较基础清洗和额外语义/执行筛选 | 记录样本差异与筛选成本；分清筛选策略和样本内容的共同影响 |

初始 QLoRA 配置为 NF4、double quant、BF16 计算、rank=16、alpha=32、dropout=0.05、micro-batch=1、梯度累积=8、学习率=1e-4、warmup ratio=0.03、梯度裁剪=1.0、梯度检查点开启。第一轮序列长度为 2048；长轨迹使用经显存验证的 4096 配置，并单独报告长度分布。

主线训练 1 个 epoch，每 100 optimizer steps 验证并保存，最终也验证和保存；checkpoint 根据 dev 指标选定。若验证结果支持继续训练，第二个 epoch 作为独立续训实验，不能静默延长。

优化器使用 AdamW；具体实现、dtype 和软件版本必须记录。用第一个通过 E01—E07 的依赖组合生成精确版本锁，正式实验不自动升级。packing 首轮关闭，开启 packing 属于额外效率实验，必须重新检查边界与监督遮罩。

学习问题：loss 下降为什么不能证明工具选择更好？QLoRA 四位存储与 BF16 计算分别影响什么？

### D. Pi 数据与任务迁移

Pi 任务至少覆盖八类：读取定位、结构化配置修改、小函数修复、多文件一致性修改、测试失败恢复、缺参数询问、无需工具回答、无效路径或空结果恢复。使用小型可执行仓库，成功判据由文件状态和测试定义。

训练轨迹目标为 1,000 条有效记录；dev 为 40 个独立任务，最终 test 为 100 个独立任务，每类至少 10 个。剩余任务用于增加较难类别，分配规则在 test 冻结前写入清单。训练任务与测试任务不得共享模板族或仓库族。

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E13 | 通用 SFT 模型进入 Pi | 相同工具定义、任务、步骤预算和模板 | 保存实际 Agent 事件、调用与最终状态；定位协议问题和能力问题 |
| E14 | 增加 Pi 训练轨迹 | 与通用 SFT 对照；公开/领域数据比例为独立变量 | 在 dev 上验证迁移收益和通用回归；不能只测训练过的仓库 |

统一使用该 Pi 版本实际暴露的 read、edit、write、bash 工具定义，保存 schema 哈希。接入验证包括流式 tool_calls、调用 id、工具返回匹配和会话终止。上下文不足、输出截断、工具执行错误分别计数。

任务在独立容器或经验证的隔离环境中运行。工具只能访问任务工作区，评测网络默认关闭，凭据不注入。不能把访问真实项目或外部服务的成功率与隔离任务混算。

主线任务最多 12 次工具调用，单次命令限时 60 秒，单任务限时 300 秒，上下文上限为 8192 tokens。接入服务达不到该上限时，先解决资源问题或另立条件受限的实验，不能静默减少预算。所有被截断和超时任务保留在分母中。

### E. 蒸馏

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E15 | 验证教师 | 教师量化精度、模板和预算固定；使用 dev | 确认哪些任务教师更可靠；不依赖参数量推断能力 |
| E16 | 教师生成与筛选 | 至少 2,000 个训练请求；保留成功、失败和拒绝 | 至少 1,000 条通过定义检查的有效轨迹；不足时报告覆盖和失败，不复制补量 |
| E17 | 参考监督与教师监督的匹配比较 | 共同 prompt id、相同初始学生、rank、步数和提示条件 | 用 1,000 条共同有效任务比较；记录标签长度和监督 token 差异 |
| E18 | 蒸馏规模与筛选策略 | 250/500/1,000 嵌套教师数据；筛选另立对照 | 分析规模、有效率和质量；错误教师轨迹不能隐去 |

主线是序列级蒸馏：训练目标为经过检查的教师输出和执行轨迹，不把它写成 logits/KL 蒸馏。教师只处理训练任务，不接触最终 test。

每条教师数据要检查 schema、参数引用、执行结果与任务最终状态。JSON 正确但任务失败的数据不能标为有效成功轨迹。参考监督来自独立的任务规则和可执行参考解，不能也由同一个教师生成后称为独立对照。

E17 从同一个官方学生检查点分别训练两组适配器，比较标签来源。相同样本数和 optimizer steps 下，监督 token 数仍可能不同，必须报告；再用相近训练 token 预算复核主要结论。无蒸馏的新增数据组保留，避免把更多训练数据的收益误归因于教师。

学习问题：蒸馏为什么仍使用交叉熵？过滤教师数据可能同时改变了哪些变量？

### F. 推理与量化

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E19 | 合并、转换、部署一致性 | 同一模型、同一模板；合并前后与转换后对照 | 保存权重哈希和转换命令；先检查参数、输出与工具调用格式 |
| E20 | F16、Q8_0、Q4_K_M 比较 | 同一 llama.cpp build、GPU 卸载、KV 设置与请求清单 | 比较能力、权重大小、峰值显存、TTFT 和 tokens/s |
| E21 | 上下文与并发实验 | 输入 token 档位 256/1024/4096；输出上限 128/512；并发 1/2/4 | 分开记录 prefill、decode、吞吐和尾延迟；OOM、排队和 CPU 卸载分别报告 |

性能实验每个条件预热 5 次，记录至少 30 个请求，独立运行 3 轮。请求记录实际输入与生成 token 数；tokens/s 以实际生成 token 数除以对应 decode 时间计算。不能用最大输出长度代替真实生成量。

报告 TTFT 的客户端测量定义、网络位置、采样和停止条件。呈现中位数、p95 和轮间差异；GPU 内核计时必须同步。不同后端的差异单独实验，不能与量化收益混写。内存不足的组合保持失败记录，不降低并发后沿用原配置名。

### G. 综合评测

| ID | 做什么 | 控制条件与证据 | 验收标准 |
| --- | --- | --- | --- |
| E22 | BFCL 官方检查器评测 | 锁定 bfcl-eval==2025.12.17；读取类别并冻结清单 | 对离线 AST 与工具无关性类别运行全部样本，报告具体类别、数量和版本 |
| E23 | Pi 最终任务评测 | 100 个冻结任务；各模型同样预算；每任务 3 次运行 | 保存逐任务、逐次结果；成功由独立判据确认；不以模型自述打分 |
| E24 | 通用能力回归 | lm-evaluation-harness 锁定 revision，ARC-Challenge 官方 test 全集 | 记录 task 配置、shot 数、模板和分母；检查专项训练是否引起能力变化 |
| E25 | 误差归因与重复验证 | 配对原模型、提示基线、SFT、蒸馏与量化结果 | 给出胜负对照、失败分类、区间及其条件；结论不超过证据 |

BFCL 首先在开发阶段验证 handler 与官方 checker 接口。类别 manifest 保存软件版本、数据哈希、样本 id、FC/prompt 模式与格式转换方法。快速子集只作为接口检查；最终运行不得使用 limit。只完成上述类别时，报告“BFCL 指定类别成绩”，不能称为 BFCL 全量总分或官方排行榜排名。

只用 dev 选 checkpoint 和参数，方案冻结后运行最终 test。关键 SFT 与蒸馏配置分别使用训练 seed 17、42、2026；小规模探索可以单 seed，但正式结论需要报告三次训练的平均值与波动。Pi 采样参数与每次运行 seed 一起固定；GPU 和后端不能保证的确定性要如实记录。

Pi 任务成功率按任务计；重复运行不是新增独立任务。比较模型时使用任务级配对结果与按任务聚类的 bootstrap 区间。BFCL 同时给出正确数、总数与官方类别成绩。没有统计证据时，不使用“显著提升”。

错误至少区分：工具选择、参数名或类型、参数值、应调用但未调用、不应调用却调用、返回结果理解、循环、模板/解析、执行环境、截断与超时。修复解析器后应重跑所有受影响模型，并保留修复前后的记录。

## 6. 像实验笔记一样记录

### 6.1 一份主笔记与必要原始文件

记录围绕实验问题组织。一个实验有一份主笔记，配置、指标和原始日志作为附件；不为每条命令创建一份报告，也不把记录系统做成新的工程平台。

| 材料 | 保存内容 | 如何使用 |
| --- | --- | --- |
| 实验笔记 | 问题、条件、关键过程、结果、判断与下一步 | 人阅读的主线，Markdown 与 Word 内容对应 |
| 配置文件 | 模型和数据版本、训练/推理参数、seed、代码版本 | 自动保存完整配置，正文只展示影响判断的参数 |
| 指标 CSV | step、loss、验证指标、耗时、吞吐和显存等实测值 | 自动追加，作为绘图与汇总的来源 |
| 日志与逐条结果 | stdout/stderr、报错、模型输出、工具轨迹与判据 | 查证具体问题，正文摘录必要部分 |
| 图与证据索引 | 图表原图、必要截图及其对应文件 | 确认图片来自哪次运行与哪份数据 |

实验使用 E编号，多次运行用 R01、R02 区分，例如 E09-R02；日期、seed 与参数留在配置中，不把文件名堆成一串哈希。总索引只列实验问题、状态、主要结果和笔记位置。

完整配置保存 Git commit 与工作区修改情况。未提交的代码需要保存对应 diff，否则只有 commit 不能复现。模型、数据和依赖版本记录一次并引用；不在每页重复列清单。

原始数据不覆盖。修改分析时保留前一次运行；数值更正写明原值、修正值和原因。中断、失效与失败运行保留，不能改名成成功。没有测到的指标留空，不能填零。

大型产物集中保存，按实验号归档。原始日志允许压缩，归档保存文件清单和 SHA256；指标、失败证据与关键 checkpoint 不参与临时快照清理。中断恢复先核对总索引与已有证据，再继续未完成部分。

公开仓库保存代码、配置、划分与哈希清单、必要的脱敏结果、报告和图片。模型权重、下载缓存、庞大日志、凭据及私人面试笔记留在被忽略的本地位置。公开目录树只展示实际存在并已跟踪的文件。

### 6.2 每个实验的正文结构

| 段落 | 要写什么 | 通常的篇幅 |
| --- | --- | --- |
| 这轮想弄清什么 | 一个明确问题及事前预测 | 1—2 段 |
| 怎么做 | 数据、对照、改变的变量和关键参数 | 1 张小表，加必要解释 |
| 实际过程 | 初次尝试、关键观察、遇到的问题、修改及其理由 | 3—6 个短段；复杂排错可以增加 |
| 跑出了什么 | 数值、图表、典型成功与失败样本 | 1 张结果表、1—3 张有用的图 |
| 怎么理解 | 数据支持的判断、仍不确定的部分和下一步 | 3—5 句，必要时加局限 |
| 理解与证据 | 用户的解释或未回答问题，配置和日志入口 | 简短列出 |

标题写具体问题，例如“E10：QLoRA 省了多少显存，效果是否变化”。正文自然讲清过程，不强制每段都套上“观察/假设/证据/结论”标签，但必须让读者区分实际结果和推测。

归纳时保留关键转折：为什么换参数、触发了什么错误、尝试过什么、哪次修改有用、哪些条件下仍失败。安装输出、重复命令和冗长堆栈移到原始附件，正文保留有辨识度的错误片段及解释。

不能只留下最终成功配置。影响后续选择的失败尝试要有条件、结果与处理过程；无关的重复尝试可以用一段话合并，并列出对应运行号。若改变了最初判断，说明哪份证据促成了改变。

单个普通实验正文目标为 2—5 页；复杂实验可以更长，不为满足页数删除必要过程，也不为凑页数加入概念综述。用户理解反馈单独保留，自动整理不能代填或改写。

### 6.3 Word 分册与适度归纳

Word 按阶段形成有限篇幅的实验册，拟分为“环境与训练机制”“微调与数据”“蒸馏”“推理与 Agent 评测”。每册目标 12—25 页，预计超过 30 页时在完整实验的边界处分成上下册。

每册先用 1—2 页概述本阶段的问题、实验关系和主要结果，再保留各实验的关键过程。章节通过实验号引用原始附件；不用重复粘贴全量配置、逐条输出和日志。

同一实验持续编辑既有章节：新曲线替换旧临时图，新汇总更新结果表；新的重要失败保留为过程段落。运行中的状态更新不新增一个章节，不能让文档随训练步数无限增长。

阶段结束做一次归纳，保留关键尝试与解释，合并重复信息。新增“本阶段学到什么”时必须指向实际实验和证据。最终项目总结目标为 6—10 页，跨阶段比较并引用实验册，不再复制各册全文。

一个轻量总索引连接各册、实验号和附件。分册、页数目标和总结篇幅是组织方法；实验规模与正式验收要求不因此减少。

### 6.4 更新频率与文件保护

训练指标按日志频率实时写入 CSV，模型与工具输出按实际运行保存。Word 在训练开始、关键变化、checkpoint、评测批次完成、报错和结束时更新；长任务至少每 10 分钟更新当前实验的临时结果段落。

更新结果要标明截至哪个 step 或时间。新数据覆盖当前临时汇总，保留原始曲线数据；阶段结束再写最终结论。图表在 checkpoint 或阶段结束时更新，没有足够数据时不画趋势。

Word 写入前保留上一个可用版本。文件被打开锁定时另存时间戳快照，之后再同步；不关闭用户的 Word 窗口。临时快照默认保留最近 5 份，阶段结束留下最终稿与一份上一版；原始数据与有意义的失败记录不参与这种清理。

记录中断后检查最后的配置、指标、日志和 checkpoint，再确定续跑还是重跑。文档延迟与同步失败如实说明，不把文档更新失败当作训练失败，也不在未结束时填写最终结果。

## 7. 技术博客风格与图表规范

### 7.1 语言

面向未来复习项目的人，用技术博客的语气说明问题：先说正在解决什么，再讲做法、数据和理解。术语首次出现时用一句普通话解释，之后直接使用；公式仅在帮助理解机制时出现，并解释变量。

用具体的动作和事实，少用抽象口号。写“把长度从 2048 改为 4096 后出现显存不足，随后检查激活内存”，不要只写“进行了深入优化”。这只是句式示例，实际文档中的操作和结果必须来自真实实验。

一个段落解释一个主要判断。优先用连贯短段落，参数或结果适合比较时才用表格；不把每句话拆成项目符号，不反复使用“首先、其次、最后、综上所述”。

章节按实验的实际思路组织，问题旁先给已有答案，再沿着排查、观察和判断展开。不机械重复六个模板标题，不把正文写成状态清单；读者应能顺着段落理解为什么这样做、遇到了什么，以及结果改变了哪个判断。反馈状态和归档信息放在总结后的索引，不打断博客正文。

关键步骤配短代码块，摘录实际实现的核心逻辑或等价示例，交代所用变量和它解决的问题；不整段粘贴脚本。Markdown 使用带语言的围栏，Word 使用等宽字体、浅色底纹和中文注释，保持缩进并检查长行、换行和分页。

允许自然的复盘口吻，但不伪造“我已经掌握”或未做过的操作。避免论文式概念铺陈、营销式赞美和没有数字支撑的“显著提升”“全面赋能”“深入探索”。不为了去 AI 味刻意添加口头禅、错别字或私人故事。

图表后用 2—4 句回答：最明显的变化是什么，能支持什么，不能解释什么，接下来如何验证。不要把图上每个数值再重复一遍，也不能让读者自行猜结论。

### 7.2 Word 与 Markdown 的视觉风格

| 项目 | 规范 |
| --- | --- |
| 纸张与边距 | A4；上下 2.2 cm，左右 2.0 cm |
| 字体 | 中文微软雅黑，英文和数字 Calibri，代码 Consolas；使用可显示中文的回退字体 |
| 正文 | 11 pt、1.25 倍行距、段后 6 pt；长段落适度拆分 |
| 标题 | 文档标题 20 pt；一级 16 pt、二级 13 pt、三级 11.5 pt；最多三级 |
| 配色 | 白底、深灰正文、深蓝标题；表头浅灰，不使用大面积渐变或装饰背景 |
| 表格 | 优先 3—6 列，表头重复，单位写在列名；过宽时拆表，不能不断缩小字体 |
| 图片 | 通常宽 14—16 cm；居中；图号与说明紧邻图片；关键字在正常比例下可读 |
| 页眉页脚 | 阶段名称与页码，避免每页重复一整套实验元数据 |

Markdown 保留相同的章节与图表顺序，使用标准标题、表格、图片与相对附件链接。两种形式的数值、结论和实验状态一致；Word 的排版不改变内容含义。

已执行实验以“问题与结论”开头，在问题旁说明实际验证出的答案和边界，再展开方法与过程。复习题附参考解释，用户理解反馈仍单独保留，未回答不代填。正文不列实际文件路径；数据、运行档案与附件位置统一放在阶段总结之后的证据索引，避免路径打断阅读。

标题与后续内容保持在同页，表格按合理行高分页，图与图注尽量不拆开。生成后检查中文缺字、表格越界、空白页、页码和图注；Word 中图片必须内嵌。复杂表格与图片页需要实际渲染检查。

使用 Word 实际导出 PDF，再渲染为页面图片进行视觉检查。首次模板和每册定稿检查全部页面；后续更新检查新增或修改页。只有实际查看图片后才记录视觉核验完成，文件成功写入不能代替排版核验。

### 7.3 图表的共同规则

实验图使用标准绘图库，从原始 CSV/JSONL 生成；保存绘图脚本、输入文件和导出 PNG，默认 300 dpi。曲线、柱图与文字截图不通过图片生成模型伪造。

每张图包含具体标题、横纵轴名称、单位和必要图例。图注给出实验号、样本数或运行次数、关键对照条件及数据入口。图中的中文必须正常显示，数字和线条在 Word 正常缩放下清晰。

同类模型在整套报告中保持颜色一致：原模型灰色 #6B7280，提示词基线蓝色 #2563EB，SFT 绿色 #059669，蒸馏橙色 #D97706，量化紫色 #7C3AED。同类配置用线型或标记区分，避免只靠颜色辨认；默认一图不超过 5 条主曲线。

柱状图纵轴从零开始，折线图可以收窄范围但刻度必须清楚。坐标使用对数尺度时明确标注。不用三维柱图、双纵轴制造相关性，也不用饼图表达训练趋势。

正文中的百分比通常保留 1 位小数，耗时和吞吐保留 2—3 位有效数字，同时保留原始精度。成功率同时给出正确数/总数。没有数据不画点，失败条件不填零，也不通过移除失败样本改善曲线。

### 7.4 Loss 曲线

横轴首先使用 optimizer step，不能与 micro-step 混淆；比较不同有效 batch 或数据规模时，增加 seen tokens 或 epoch 的图，解释训练预算是否可比。纵轴标为交叉熵 loss，并说明监督位置。

训练 loss 用实线；验证 loss 用实际评估位置的点或虚线。不能插值出不存在的验证测量。不同 loss mask 或目标分母的 loss 分开呈现，不能直接用其数值高低判断能力。

优先显示原始曲线；需要平滑时，原始线以较淡颜色保留，并在图注写窗口大小。不能只显示平滑后的下降趋势。三次训练可呈现均值和标准差带，同时保留单次曲线或散点；清楚说明阴影是标准差还是置信区间。

图中可以标记 checkpoint、学习率变化和异常位置，但解释必须来自日志。训练集与验证集分歧、loss 波动和 loss 下降而任务无改善，都应在正文讨论。

### 7.5 模型表现比较

工具调用、BFCL 类别和 Pi 成功率采用分组柱图或点图，附一张数值表。不同评分定义的指标分别绘图，不把它们平均成自创的“综合能力分”。

原模型、提示词基线、SFT、蒸馏与量化必须在相同任务、模板和预算下比较。每组标出样本数与运行次数；三次训练的点或波动可见，不能只画最优一次。

区间计算匹配数据结构：独立二项结果可使用 Wilson 区间；Pi 的三次运行按任务聚类，使用任务级 bootstrap；训练 seed 的波动另行描述。不能把 100 个任务各跑 3 次当成 300 个独立任务。

训练数据增大带来的变化用折线或点图，横轴是真实独立样本数或监督 token 数。解释新增数据的类别变化，避免把数据量、数据质量和教师来源混为一个变量。

### 7.6 推理性能与错误分析

延迟统一使用 ms 或 s，吞吐使用 tokens/s，显存使用 MiB 或 GiB；同一比较图不混用单位。TTFT、decode 速度、请求总时间分开说明，冷启动与预热结果分开比较。

并发与上下文比较用折线或分组图，显示中位数、p95 与独立运行波动；质量与成本的取舍可以用散点图，标出具体配置。每个点都对应实际配置，不绘制想象中的趋势线。

错误分析优先用横向条形图，按数量排序。写明统计分母和错误类别是否互斥；一个样本有多个错误标签时不能把标签数当作失败任务数。配合少量真实样本解释主要错误，不能只给一张图。

### 7.7 截图与解释图

截图用于保留真实界面、典型输出或排错现场。记录运行号和时间，裁掉无关信息；截图不能代替结构化指标。日志转录图标注“由日志渲染”，不能冒充桌面截图。

token/mask 示意、数据流和流程图标注为解释图或设计图，结合真实样本帮助理解。它们不计作训练完成证据。Word 内嵌原图，另存源图便于复查和重新排版。

## 8. 正式完成的判定

主线完成需要 A—H 的交付物齐全，E00—E25 有已执行记录或明确可复现的失败记录，并且核心 10k SFT、匹配蒸馏、Pi 100 任务、BFCL 指定类别全集、通用回归和性能比较实际执行。遇到设备或环境问题未完成的部分明确列为未完成，不能只写脚本就验收。

项目不预设分数必须上涨。完成公平对照、解释负结果并留下可复现证据，也是有效实验结论。训练机制验证必须通过，否则后续性能数字不作为训练效果证据。

E00—E07 为前置正确性检查，不能单独作为“完成大模型训练项目”的简历证据。最终报告同时说明任务范围、硬件条件、运行数量和无法支持的外推。

项目进行中每完成一个完整学习单元整理一次中文复盘。面试材料引用具体实验 ID，区分实际做过、阅读理解和未来工作；用户未回答的理解问题不代填。

## 9. 后续扩展的进入条件

4B 学生扩展在 1.7B 主线正确性、环境和记录系统稳定后开始，用同一数据与任务研究容量差异。进入前通过显存与上下文检查，不能用较小预算的 4B 结果直接比较主线。

logits/KL 蒸馏作为第二种蒸馏方法单独设计，先检查词表对齐、温度、损失组合和 logits 存储成本。未经该实验不能声称掌握概率分布蒸馏。

从零预训练作为独立分支：使用约 64M 的小型 decoder-only 模型，固定 tokenizer、训练 token 预算和独立验证集，研究 loss/perplexity 与规模。结果与 Qwen 后训练分开报告，不称为从零训练 1.7B 模型。

DPO、GRPO、推测解码与 vLLM/SGLang 并发服务各自需要新实验设计。主线结束前不通过增加技术名称代替已经要求的对照与复盘。
